# 要件

## 背景

- 元のスキル i-have-adhd は、英語圏の汎用の決まり10個を持つ。利用者はこれを他の人が作った物としてそのまま使っていた
- 利用者の過去60日のログの調査で、元の決まりが扱わない読みにくさが見つかった（仮説 H1〜H7）
- 決まりを CLAUDE.md に書くと、スキルと二重になり、ぶつかりの解決も別の場所に散る。このため、1つのスキルに入れる

## 機能要件

### FR-A 元から残す決まり

| ID | 要件 |
|---|---|
| FR-A1 | 元の決まり1〜10と、「決まりを破る場合」「送る前の確認」を残す。決まり5と9は、後述のとおり直す |
| FR-A2 | SessionStart フックによる常時有効の仕組みを残す。印のファイル名と本文の文言は変える |
| FR-A3 | eval の仕組み（`scripts/run_evals.py`、`evals/`、`tests/test_run_evals.py`）を残す |

### FR-B 足す決まり（すべてのセッション向け）

| ID | 決まり | 出どころ |
|---|---|---|
| FR-B1 | 判断は1件ずつ出す。複数あれば「N件あります」と1行で言い、1件目を出す。答えをもらってから次を出す | 答1・答9、H2 |
| FR-B2 | 判断を聞く1回ごとに、その返事だけで答えられるように書く。どのタスクか／何を決めるか（1文）／なぜ今か／各案の中身（選ぶと誰が何をするか）／おすすめと理由1つ。AskUserQuestion でも同じ | 答7、H2・H3 |
| FR-B3 | 分かりにくい内容は、「誰が・何を・どこへ」の流れで書く。1文に1つの事だけ | 答5、H1 |
| FR-B4 | 「〜という理解で合っていますか」には、冒頭で はい／いいえ、続けて根拠1〜2点 | 答6、H6 |
| FR-B5 | 返事は、読み手が使っている言語で書く。見出しの語（「Next:」など）も同じ言語にする。コマンドとコードは除く | H5 |
| FR-B6 | 質問の答えと関係ない運用の情報（片付け、監視の経緯）を、報告に混ぜない | H4 |
| FR-B7 | 読み手の操作が要る時は、1行目を「あなたの操作:」にし、番号付きの手順を続ける | 答4、H7 |

### FR-C 足す決まり（複数のエージェントをまとめて報告するセッション向け。スキル内の独立した節）

| ID | 決まり | 出どころ |
|---|---|---|
| FR-C1 | 報告済みと同じ通知（完了の重複、監視の期限切れ、起動時の既存の完了行）には、台帳の更新と、括弧書きの1行だけで返す。新しい完了は普通に報告する | 答3、H4 |
| FR-C2 | 決定待ちは、会話が一段落した時に、溜まっていれば知らせる。毎回の報告の末尾には付けない。話の途中では割り込まない。操作待ち（FR-B7）と blocked は、すぐ知らせる | 答2、H3 |
| FR-C3 | 「全体の状況」は、決定待ち、作業中、完了の順。1エージェント1行。決定待ちの行には「何を決めるか」を書く | H3 |
| FR-C4 | エージェントから長い報告が届いたら、判断を1件ずつに分ける（FR-B1）。ファイルの場所と行番号は、判断に要る時だけ書く | H2 |
| FR-C5 | 台帳（TASKS.md など）の1行は、タスク40字＋結果ファイル、状態は「状態＋待っている物」30字。経緯は書かない | 答8 |
| FR-C6 | エージェントを起動した直後に、読み手の操作が要る画面で止まっていないかを1回確かめる。止まっていれば FR-B7 の形で知らせる | 答4、H7 |

### FR-D ぶつかりの解決

| ID | 要件 |
|---|---|
| FR-D1 | 元の決まり5「毎ターン状態を言い直す」と、FR-C1「報告済みと同じ通知は括弧書きの1行」を、スキル内で両立させる。括弧書きの1行は、状態の言い直しを最小にした形とする。この1行には、いま読み手を待っている物を書く。何も待っていなければ、その旨を書く |
| FR-D2 | 元の決まり1「最初の行は次の行動」と、FR-B2・FR-B7 の形は、衝突しない。判断の依頼では、タスクの印と「何を決めるか」の行が、最初の行にあたる。操作が要る時は「あなたの操作:」が最初の行にあたる |
| FR-D3 | 元の決まり9「リストは5件まで」と FR-B1 は、「判断は1件、一覧は5件まで」で両立させる |
| FR-D4 | 元の決まり10の禁止（前置き）と、FR-B1 の「N件あります」の1行は、「N件あります」が前置きではなく依頼の一部であるため、衝突しない。本文に明記する |

## 非機能要件

| ID | 要件 |
|---|---|
| NFR1 | 名前を変える: plugin 名、スキル名、marketplace 名、印のファイル、止める言葉を `adhd-report` にする。元の plugin と並べて入れても取り違えない |
| NFR2 | LICENSE は元の著作権表示を残し、自分の分を足す。README に、元のリポジトリと作者を書く |
| NFR3 | スキル本文は英語で書く。例は日本語の場面を入れてよい |
| NFR4 | 常時有効のフックは、失敗してもセッションの開始を止めない（exit 0）。POSIX sh で動く |
| NFR5 | 本文の増加を抑える。フックが毎回注入するため、元の約2倍以内に収める |
| NFR6 | README.md（英語）と README_ja.md（日本語）を同じ内容で用意し、先頭に言語の切り替えの行を置く |
| NFR7 | Claude Code 専用にする。Codex・Gemini・Cursor 向けの設定は、保守の対象外にして削除する |

## 範囲外

- 元の plugin の削除・無効化、`~/.claude` と nix の設定の変更、新しい plugin のインストール（入れ替えは利用者の判断の後）
- GitHub のリポジトリ作成と push
- chief-of-staff の `bin/watch-agents.py` と、タブ名の【操作待ち】の表示
- 外部 API を使う eval の実行

## 受け入れ条件

1. `python3 -m unittest discover -s tests` がすべて通る
2. `python3 scripts/run_evals.py validate` が通る
3. 本文、manifest、フックに `i-have-adhd` の名前が残らない（LICENSE、README のクレジット、docs の出どころの記述を除く）
4. FR-B・FR-C の各決まりに、本文の見出しとテストが対応する
